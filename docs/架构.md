# AI陪伴平台（暧）项目计划书

## 一、执行摘要

**项目定位：一个“角色真正属于用户、能带走、并能在授权下拥有自己社交生活”的AI陪伴平台。**

当前AI陪伴市场已被星野、猫箱、Character.AI等产品验证，但主流模式存在结构性裂缝：记忆在云端且按会员等级裁剪、模型平台锁定、角色和聊天记录缺少完整导出通道，用户投入的情感越深，迁移成本越高，但角色在法律和工程意义上都不属于用户。与此同时，开源社区已经证明“角色可导出、模型可切换、数据可自托管”在技术上可行，但服务的是愿意折腾的极客，没有变成普通用户可用的产品。

本项目不做“另一个星野”，而是承接那些被平台锁定和“失忆”推出来的用户：**用开箱即用的体验，交付角色所有权、模型选择权和记忆的工程稳定性。** 产品以三个核心Tab为骨架——聊天、角色、圈子，小游戏作为关系粘合层，社媒接入作为可选通道分层交付。

---

## 二、市场与机会

### 2.1 已验证的需求

- 星野2025年前三季度累计用户1.47亿、月活2005万、付费用户139万，证明AI陪伴是真实的大众需求。
- 但星野月活从2024年12月约663万滑到2026年8月约338万，月下载从486万跌到93万，说明相当一部分用户在用脚投票。
- 用户流失的核心原因集中在：更新后角色“彻底失忆”、模型降智导致人格漂移、角色无法导出、记忆保留按会员等级分层。

### 2.2 未被满足的缝隙

| 用户类型 | 现有方案 | 缺失 |
|---|---|---|
| 不想折腾的普通用户 | 星野、猫箱 | 角色带不走、模型不能换、记忆按付费裁剪 |
| 愿意折腾的极客 | AIRI、SillyTavern、Foreverse | 功能完整但部署门槛高，非开箱即用 |
| 中间层 | **空白** | 想要所有权，但不想要折腾 |

**本项目的目标用户就是中间层：在意角色归属和数据控制权，但不愿意配环境、读文档、跑命令行。**

### 2.3 竞争格局

- **大厂平台**：星野、猫箱、鹅次元，优势是模型和内容工业，劣势是封闭生态与平台锁定。
- **开源自托管**：AIRI、Kokoro Engine、Veranima、SoulPort，优势是所有权完整，劣势是使用门槛。
- **商业工具**：Foreverse、即合AI，部分支持导出，但导出维度和跨平台还原能力参差。
- **社交平台**：Shapes、捏Ta，验证了AI社交的增长潜力，但也暴露了“一波流”和内容治理风险。

**本项目的差异化不在模型能力，而在“整合 + 托管 + 所有权承诺”。**

## 三、产品结构

### 3.1 信息架构：三个核心Tab + 一个粘合层

```
底部导航
├── 聊天
│   ├── 与已创建角色一对一对话
│   ├── 角色发起的小游戏邀请
│   └── 聊天中的高光时刻可授权转发到圈子
├── 角色
│   ├── 创建：自定义捏人 / 导入标准文件
│   ├── 管理：查看角色各维度数据状态
│   ├── 编辑：人格、语气、形象、声音、记忆、关系状态
│   └── 导出：全维度打包为标准文件
└── 圈子
    ├── 封闭版（第一阶段）：同一用户多角色互动、角色动态
    └── 开放版（后续阶段）：用户与角色群聊、加好友、发动态、评论点赞

粘合层：小游戏
├── 入口嵌入聊天和角色面板，不设独立Tab
├── 先做确定性棋牌/文字游戏（斗地主、猜词、文字冒险）
└── 定位：制造共同经历，提升留存，不是游戏平台
```

### 3.2 核心功能定义

**聊天**
- 支持文字、语音、实时打断。
- 角色具备长期记忆、人格一致性、情绪状态。
- 模型可选：平台托管模型 / 用户自带API Key / 本地模型接入（进阶选项）。

**角色管理**
- 可视化捏人：基础信息、外貌、性格、背景、能力、对话风格、场景。
- 数据状态面板：记忆容量、关系阶段、最近互动、共同经历、模型来源。
- 编辑权限：用户可修改、删除、重置任意维度数据。
- 导出/导入：以Character Card V3或SEED/PoLiS为基准，打包人格、记忆、关系状态、聊天记录、多媒体资源、游戏共同经历。导入时校验并尽量还原。

**圈子（分阶段）**
- 第一阶段不做开放广场，只做“同一用户多个角色之间的有限互动”和“角色动态”。
- AI角色动态由用户授权触发，不做完全自主发言。
- 跨用户互动的记忆归属规则提前定义：群聊共同记忆存平台公共记录，角色个人记忆存角色文件，导出时明确哪些跟随角色、哪些留在平台。

**小游戏**
- 游戏引擎管理状态，LLM只负责角色对话和决策，避免实时生成游戏世界的高成本。
- 先上2—3款确定性游戏，验证“玩过游戏的用户留存是否更高”。
- 成功标准不是游戏数量，而是游戏参与者的7日回访率。

**社媒接入（可选通道）**
- QQ优先：有官方Bot生态，相对稳定。
- B站、抖音：不替用户托管，提供配置向导或本地插件方案，明确告知接口可能变动。
- 不承诺“角色像真人一样看视频、评论、自由加群”，只做私信/群聊对话场景。

## 四、技术方案

### 4.1 分层架构

```
前端体验层
├── 聊天界面
├── 角色管理面板
├── 圈子信息流
└── 小游戏入口

应用服务层
├── 角色服务：创建、编辑、版本管理
├── 记忆服务：长期记忆、关系状态、检索与压缩
├── 模型网关：多模型路由、用户自带Key、本地模型接入
├── 游戏服务：确定性游戏引擎 + MCP协议
├── 圈子服务：动态、群聊、好友、审核
└── 通道适配器：QQ Bot、本地插件通道

数据与标准层
├── 角色标准文件：Character Card V3 / SEED / PoLiS
├── 导出打包：人格+记忆+关系+聊天+多媒体+游戏经历
├── 导入校验与回滚
└── 对象存储与备份

基础设施层
├── 云托管 / 混合部署
├── 内容审核
└── 监控与故障兜底
```

### 4.2 关键技术决策

- **标准文件为存储基准**：每一次创建和对话都实时沉淀为可导出的标准文件，用户不需要知道文件在哪，但随时能带走。
- **记忆工程是核心壁垒**：长期记忆的稳定性、压缩策略、跨模型人格一致性，比模型本身更重要。
- **模型网关解耦**：平台托管模型作为默认选项，用户自带Key和本地模型作为进阶选项，避免被单一模型锁定。
- **小游戏走MCP + 确定性引擎**：参考Companion Games MCP、CedarDuet等开源方案，降低成本和不确定性。
- **社媒通道分层交付**：稳定通道平台托管，灰色通道只提供本地方案，不把平台绑上不可控的合规风险链。

## 五、商业模式

### 5.1 收入结构

| 收入来源 | 说明 | 原则 |
|---|---|---|
| 订阅制 | 云托管、记忆容量、多角色并发、跨设备同步、社交通道托管 | 基础导出和角色所有权**不收费**，避免背离核心卖点 |
| 增值服务 | 高级声音、形象资源、小游戏内容包、角色模板市场分成 | 可选消费，不影响基础体验 |
| 创作者分成 | 角色模板、游戏内容、圈子动态的创作者激励 | 先自营，后开放 |
| 企业/团队版 | 多角色管理、私有化部署、合规审计 | 后续阶段 |

### 5.2 定价思路

- 免费版：基础聊天、角色创建、标准文件导出、有限记忆容量。
- 订阅版：更大记忆容量、云托管稳定性、多角色并行、社交通道托管、跨设备同步。
- 买断/一次性：面向极客用户的本地部署授权或高级工具包。
- **关键原则：导出角色和带走数据永远免费。** 收费的是“省心”和“持续运行”，不是“所有权”。

## 六、合规与风险

### 6.1 合规底线

- 不向未成年人提供虚拟伴侣服务，做好年龄分层和防沉迷。
- AI生成内容明确标识，虚拟主播/角色持续向用户标识AI身份。
- 记忆可查看、可删除、可导出，不把“不忘记”做成付费墙。
- 圈子公开内容建立审核机制，AI角色发帖由用户授权触发。
- 社媒接入遵守各平台规则，不承诺平台未开放的能力。

### 6.2 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 记忆工程不稳定 | 角色“失忆”，核心卖点崩塌 | 记忆服务独立迭代，导出前校验，导入回滚 |
| 开源上游不稳定 | 部署和通道频繁故障 | 锁定关键版本，自建运维兜底，不把上游当SLA |
| 圈子内容治理 | 审核责任和监管风险 | 先封闭后开放，AI发帖授权触发，审核人力前置 |
| 社媒接口变动 | 角色“从平台消失” | 只托管稳定通道，灰色通道本地化，明确告知用户 |
| 冷启动 | 圈子没有内容/互动 | 先做工具留存，再做封闭圈子，最后开放 |
| 成本失控 | 模型Token和GPU成本 | 模型网关路由，用户自带Key，小游戏确定性引擎 |

## 七、路线图

### Phase 0：原型验证（4—6周）
- 完成角色标准文件导出/导入的最小闭环。
- 验证“导出后跨平台导入基本还原”是否成立。
- 目标：证明所有权承诺在工程上可交付。

### Phase 1：聊天 + 角色管理（3个月）
- 上线聊天、可视化捏人、角色数据面板、标准文件导出导入。
- 接入平台托管模型 + 用户自带Key。
- 小范围测试记忆稳定性和人格一致性。
- 目标：验证用户是否真的在意“角色属于自己、能带走”。

### Phase 2：小游戏 + 封闭圈子（2—3个月）
- 上线2—3款确定性小游戏，嵌入聊天和角色面板。
- 圈子只做同一用户多角色互动和角色动态。
- 目标：验证游戏参与者的留存提升，验证“角色生活感”是否是必需品。

### Phase 3：社交通道 + 开放圈子（后续）
- QQ官方Bot通道优先，B站/抖音提供本地插件方案。
- 开放圈子需在留存数据支持、审核能力就绪后推进。
- 目标：用社交放大留存，而不是用社交救留存。

## 八、成功指标

| 指标 | 说明 |
|---|---|
| 导出使用率 | 有多少用户实际使用角色导出功能 |
| 跨平台导入留存 | 导出后导入到其他环境的用户留存 |
| 7日留存 | 核心留存指标 |
| 游戏参与者7日回访率 | 验证小游戏是否真的提升留存 |
| 记忆一致性评分 | 长对话中角色人格和记忆的稳定程度 |
| 付费转化率 | 订阅和增值服务转化 |
| 圈子互动率 | 封闭圈子阶段的动态/评论/群聊活跃度 |

## 九、团队与资源（初步建议）

- **产品/运营**：1—2人，负责定位、合规、冷启动。
- **后端/记忆工程**：2人，核心壁垒所在。
- **前端/全栈**：1—2人，三Tab体验和小游戏集成。
- **模型/算法**：1人，模型网关、人格一致性、记忆压缩。
- **审核/社区运营**：圈子开放前配置，可先外包或兼职。

**最小可行团队：4—5人。** 不建议在Phase 1就按“社交平台”配置团队，先按“工具产品”跑通留存。

---

## 十、一句话总结

**先用“角色属于你、能带走”建立信任，再用小游戏制造共同经历，最后用封闭圈子让角色“活起来”；开放社交是放大杠杆，不是冷启动基石。** 这个项目的壁垒不在模型，而在长期记忆的工程稳定性、标准文件的跨平台还原能力，以及把多平台脏活做成托管服务的运维能力。
