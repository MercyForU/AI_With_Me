## 一、现状分析

### 1.1 LLM 调用位置

| 位置 | 作用 | 关键代码 |
|---|---|---|
| `server/api.js` → `/api/chat` | 主对话，SSE 流式 | `buildSystemPrompt()` → `buildContext(history)` → `llm.streamChat()` |
| `server/api.js` → `/api/characters/:id/posts` | 生成角色动态 | `POST_SYSTEM` / `POST_PROMPT`，取最近 6 条消息 |
| `server/prompt.js` | 提示词拼装 | `buildSystemPrompt(character, memories)` |
| `server/llm.js` | 供应商转发 | OpenAI 兼容 + Ollama，流式/非流式回退 |

**上下文构成（当前）**

```
system: 角色人设 + memories（最新 20 条）+ 关系阶段 + 回复规则
history: 最近 20 条消息 → buildContext 取最后 16 轮
user:    本次输入
```

溢出点就在这里：超出 16 轮的内容**直接丢弃**，没有任何压缩或召回。

### 1.2 消息数据结构

```sql
messages(id INTEGER PK, character_id INTEGER FK, role TEXT, content TEXT,
         kind TEXT DEFAULT 'text', created_at TEXT)
-- kind: text | game | error(仅前端临时)
```

### 1.3 存储方式

- SQLite（`node:sqlite`，WAL），文件 `data/app.db`
- `memories` 表：**纯手工**，每行一句话，注入时取最新 20 条
- 消息按 `character_id` 隔离，删除角色级联删除

### 1.4 已有的可复用点

- 所有数据读写都收敛在 `lib/api.ts`，没有 SQL 泄漏到组件 → **三端换实现成本低**
- `providers` 表已支持多供应商 + 加密 Key，扩展 `kind` 字段即可分类
- 前端已有「非阻塞进度」的 UI 模式（toast / 卡片状态）

## 二、与既有决策的冲突（需要你拍板）

你的需求写的是 **Tauri + fastembed（Rust）**，但我们上一轮定的是 **Electron + 现有 Node 后端**。

| | 方案 A：Electron + onnxruntime-node（推荐） | 方案 B：Tauri + fastembed |
|---|---|---|
| 后端 | 现有 `server/*` 直接复用 | **必须用 Rust 重写** api/db/auth/providers（约 1500 行） |
| 嵌入 | `onnxruntime-node` 加载同一个 `model_int8.onnx` | fastembed 加载同一个文件 |
| 权重一致性 | ✅ 字节级同一份文件 | ✅ 字节级同一份文件 |
| 包体 | 90–120 MB | 8–12 MB |
| 额外工期 | **+1 天** | **+10–15 天** |
| 风险 | 低 | 后端重写引入的回归风险高 |

**"字节级一致"的约束是同一份 `.onnx` 文件，跟用什么运行时无关。**
建议走 A：模型文件、分词、池化策略都按你的规范做，只是运行时换成 `onnxruntime-node`。

> 若你坚持 Tauri，还有折中方案 C：Tauri 壳 + Node sidecar（Rust 只做 embedding）。复杂度最高，不建议。

## 三、可行性核查结果（已实测）

| 项目 | 结论 |
|---|---|
| `node:sqlite` 支持 FTS5 | ✅ 可用（SQLite 3.51.2） |
| FTS5 `unicode61` 中文子串 | ❌ **搜「大白饭」命中 0**（整段中文被当成一个 token） |
| FTS5 `trigram` 中文子串 | ✅ **命中 1**，英文也正常 → **必须用 trigram** |
| `dust-embeddings-capacitor` | ✅ 存在，v0.1.4（2026-03 起），API 含 `loadModel({modelPath})`、`embed({pooling:'cls'})`、WordPiece、VectorMath |
| 该插件 Web 端 | ❌ **是 stub，调用即抛异常** → 浏览器端不能用它 |
| `Xenova/bge-small-zh-v1.5` | ⚠️ 本机访问 huggingface 被网络拦截，**未能当场核验**；下载脚本里加 SHA256 校验 |
| 模型体积 | INT8 约 23.9 MB，512 维输出，符合预期 |

## 四、总体设计

### 4.1 核心思路

**记忆 = 被挤出上下文窗口的那部分对话。**

不额外做「总结」，也不重复嵌入当前窗口内的内容。当历史超过 16 轮时，把最早挤出窗口的消息压成 chunk 入库，向量化后供后续召回。

这样有三个好处：
1. 天然去重（同一段内容只会被压一次）
2. 不需要额外判断"什么时候该记"
3. 记忆量随对话自然增长，与上下文窗口严格互补

### 4.2 数据模型（新增）

```sql
CREATE TABLE memory_chunks (
  id            TEXT PRIMARY KEY,        -- uuid，为将来同步预留
  character_id  INTEGER NOT NULL,
  session_id    TEXT NOT NULL,           -- 会话标识（同日 + 间隔<30min 视为同一会话）
  content       TEXT NOT NULL,           -- 拼接原文，用于展示与注入
  msg_from      INTEGER,                 -- 起止消息 id，便于回溯
  msg_to        INTEGER,
  token_count   INTEGER NOT NULL,
  content_hash  TEXT NOT NULL UNIQUE,    -- 去重
  embed_model   TEXT,                    -- 'bge-small-zh-v1.5-int8'
  embed_dim     INTEGER,
  vector        BLOB,                    -- Float32Array，512*4 = 2048B
  embedded_at   TEXT,
  created_at    TEXT NOT NULL,
  deleted_at    TEXT
);

CREATE INDEX idx_chunks_char ON memory_chunks(character_id, created_at);

-- 独立 FTS 表，trigram 分词，手工同步（不用触发器，逻辑更可控）
CREATE VIRTUAL TABLE memory_fts USING fts5(
  chunk_id UNINDEXED, content, tokenize='trigram'
);

-- 重建任务状态（单行）
-- settings 表新增 key: embed_job = {model, total, done, started_at}
```

**`memory_chunks` 不参与云同步**：它是从 messages 派生的数据，每台设备本地重建即可。这样既避免向量跨模型不兼容，也让同步体积减半。

### 4.3 分块策略

```
触发：某角色未分块的消息数 ≥ 8 条，且最早一条已滑出 16 轮窗口
切分：按时间间隔（>30 分钟）和条数（≤8 条 / ≤400 token）切
重叠：相邻 chunk 共享 1 条消息，避免语义被切断
只处理：role ∈ (user, assistant)，kind ∈ (text, game)
```

### 4.4 召回（两路 + RRF）

```
query = 当前用户输入（+ 最近 1 轮用户消息，提升指代消解）
  ├─ 向量路：embed(query) → 暴力余弦 vs 该角色所有 chunk → top 20
  └─ 关键词路：FTS5 trigram MATCH → top 20（兜底人名/项目代号/报错信息）
融合：RRF，k=60 → 取 top 6
过滤：character_id 精确匹配、deleted_at IS NULL
```

- 向量路只比对 `embed_model = 当前模型` 的 chunk（重建期间旧向量不参与，避免跨模型比较）
- 关键词路不受模型影响，重建期间照常可用 → **检索不中断**
- 1 万条以内暴力扫描：512 维 × 1 万 = 512 万次乘加，Node 约 20–40 ms，可接受

### 4.5 注入

```
system prompt 追加段落：
  【你记得的这些往事】（按时间标注，仅在与当前话题相关时自然提及）
  - [11月10日] 用户说他下周三有面试，很紧张…
  - [11月12日] 你们玩石头剪刀布，他连输三局…

预算：chunk 注入总量 ≤ 800 token，超出按 RRF 排名截断
```

与现有 `memories`（手工长期事实）**并存**：事实在前，往事在后。

### 4.6 嵌入运行时抽象（三端共用一套接口）

```ts
// lib/embedding/types.ts
export interface Embedder {
  id: string;      // 'bge-small-zh-v1.5-int8'
  dim: number;     // 512
  embed(texts: string[]): Promise<Float32Array[]>;
}
```

| 端 | 实现 | 说明 |
|---|---|---|
| 网页 / EXE | `server/embedding/onnx.ts` | `onnxruntime-node` + WordPiece（tokenizer.json），CLS pooling + L2 |
| APK | `lib/embedding/capacitor.ts` | `dust-embeddings-capacitor`，`pooling:'cls'` |
| 自定义 API | `server/embedding/remote.ts` | OpenAI 兼容 `/v1/embeddings` |

> 浏览器端若也要跑（不经本机服务），需接 `@xenova/transformers`（WASM），**首期不做**。

### 5.1 表结构

### 5.2 各类别定位

| kind | 是否必需 | 内置方案 | 用户可改 |
|---|---|---|---|
| `chat` | ✅ 必需，没配不能用 | 无 | 任意 OpenAI 兼容 / Ollama |
| `embedding` | 默认内置 | **本地 bge-small-zh-int8** | 可换成任意 `/v1/embeddings` |
| `image` | ❌ 可选 | 无 | 预留占位 |
| `tts` | ❌ 可选 | 浏览器 `speechSynthesis` | 预留 |
| `stt` | ❌ 可选 | 浏览器 `SpeechRecognition` | 预留 |

**取舍说明（我的建议）**：语音输入/朗读先用浏览器原生能力（免费、离线、中文可用），不占用供应商配置；生图目前只有「生成角色头像」一个用途，先只做类型占位不实现调用。等真的需要再接 API——这样首期工作量可控，也不会把设置页变成一堆空表单。

### 5.3 设置页结构

```

├─ 对话模型（必需）      ← 现有 UI 迁过来

│   ├─ 内置：bge-small-zh-v1.5-int8（23.9MB，本地运行）
│   └─ 自定义：API 供应商（/v1/embeddings）
├─ 语音（可选，默认用系统能力）
└─ 生图（可选，暂未启用）
```

## 六、嵌入模型切换的静默重建

**用户点切换时绝不能阻塞**。流程：

```
① 立即生效
   settings.embed_model = 新模型
   新产生的 chunk 直接用新模型入库 → 新对话的记忆正常

② 后台重建
   扫描 embed_model != 当前 的 chunk，每批 16 条
   写入 vector_v2 列（ALTER TABLE ADD COLUMN，保留旧向量）
   低优先级：批间隔 200ms，避免抢占对话请求

③ 界面
   设置页/聊天页顶部一条细进度条：「正在优化历史记忆 37%」
   不弹窗、不遮罩、可继续聊天

④ 原子切换
   全部完成后，单事务：
     UPDATE memory_chunks SET vector = vector_v2, embed_model = 新模型;
     ALTER TABLE memory_chunks DROP COLUMN vector_v2;
   期间旧向量一直可用，检索不中断
```

**重建期间检索行为**：向量路只用「新模型」的 chunk，关键词路全量可用 → 召回质量平滑过渡，不会出现"一半向量对不上"的错乱。

| 风险 | 影响 | 应对 |

## 十一、确认记录（2026-11-15 19:30）

| 决策 | 结论 |
|---|---|
| 桌面端运行时 | **Electron + 现有 Node 后端**（方案 A），后端不重写 |
| 记忆方案 | **记忆 = 被挤出上下文窗口的那部分对话**，确认可行 |
| 供应商分类 | 要加；定位是**给 AI 角色按需调用**，生成头像等聊天以外的附加能力也走它 |

### 11.1 供应商「按需调用」的设计

分类保留 `chat / embedding / image / tts / stt`，但 `image`、`tts` 不只是设置项，而是**角色可调用的工具**。

调用方式两条路，建议默认走 B：

| | A. 原生 function calling | B. 标记协议 |
|---|---|---|
| 做法 | 请求带 `tools`，模型返回 `tool_calls` | system prompt 约定 `[[img: 描述]]`，模型输出后服务端拦截 |
| 依赖 | 模型必须支持 tools | 任何模型都能用 |
| 你现有 332 个模型 | 支持度参差，中转常丢弃 tools 字段 | ✅ 稳定 |
| 实现 | 需要解析流式 tool_calls | 正则拦截 + 参数解析 |

**建议**：默认 B；检测到供应商声明支持 tools 时再启用 A。

- 命中 `[[img: ...]]` → 调生图供应商 → 图片以 `messages.kind='image'` 落库（base64 进 DB，与头像一致，便于将来同步）
- 命中 `[[tts: ...]]` → 前端朗读该段（不落库）
- 失败要降级：生图失败时把标记替换成一句人话，不能把 `[[img:]]` 原样吐给用户

### 11.2 P0 实测结果（已完成）

| 项 | 结果 |
|---|---|
| 模型来源 | `Xenova/bge-small-zh-v1.5`（经 hf-mirror 镜像，直连 HF 502） |
| 权重 | `model_int8.onnx`，**23,903,394 字节** |
| SHA256 | `b9837c19ce154ff0726d398ee77abbc03a7faf0476c6f93016c84e531be7ebb5` |
| 结构 | hidden 512 / 4 层 / 8 头 / vocab 21128（与 bge-small-zh-v1.5 一致） |
| 分词 | 中文按字切分，`大肥鱼喜欢吃大白饭` → 11 token（含 CLS/SEP） |
| 向量 | 512 维，L2 范数 **1.000000**（CLS pooling 生效） |
| 语义 | 相近句 0.9324 / 无关句 0.3866 |
| 速度 | 冷启动 326 ms；热态单条 **3 ms** |
| 其他 | 仓库里**没有** `added_tokens.json`（只有 5 个必需文件），已按实际文件下载 |

落地文件：
- `server/embedding/tokenizer.js`（WordPiece，无第三方依赖）
- `server/embedding/onnx.js`（onnxruntime-node，CLS + L2，批量 padding）
- `scripts/fetch-model.mjs`（镜像下载 + SHA256 校验，`--verify` 只校验）
- `.gitignore`（排除 `models/`、`data/` 等）

> 注：`server/` 是 CommonJS，故实现文件为 `.js` 而非原计划的 `.ts`。

## 十二、数据边界修订（2026-11-15 19:50）

### 12.1 记忆改为常驻

取消「记忆开关」。记忆是常驻能力：每轮对话后自动分块入库，每次回复前自动召回。

保留的运维操作只有两个（都在设置里）：
- 查看条数 / 最近召回示例
- **清空记忆库**（删 chunks + FTS + 重置重建任务；不影响消息与角色）

验收标准相应调整：原「关闭记忆后不写入不检索」作废。

### 12.2 数据分域：角色域 vs 聊天域

| | 角色域 | 聊天域 |
|---|---|---|
| 内容 | `characters`、`memories`(facts)、头像、关系等级、`providers`/`settings` | `messages`、`memory_chunks`、`memory_fts`、`game_records`、聊天图片 |
| 同步 | ✅ 参与 | ❌ 不参与 |
| 导出 | ✅ 角色卡 | ❌ 不导出（或走另一条链路，本期不做） |
| 主键 | 必须 **UUID**（多端新建会撞号） | 保持 `INTEGER` 自增即可 |

**这是本轮最大的简化**：消息是数据量的大头（也是冲突最难处理的部分），把它排除在同步之外，
同步只剩「角色 + 记忆事实」这种小体量、低频写入的数据，记录级增量会非常简单。
之前担心的「消息 UUID 迁移 + 时钟偏移导致顺序错乱」两个难题直接消失。

**代价**：换设备后聊天历史不带过去。你已确认接受。

### 12.3 角色卡的导出范围调整

现在 `buildCardFile()` 会把 messages / memories / games 全打包。按新边界改为：

| 字段 | 是否导出 |
|---|---|
| 人设（name/emoji/accent/tagline/personality/scenario/greeting/memory_note） | ✅ |
| 头像 | ✅（base64 内嵌） |
| 长期记忆 facts | ✅ |
| 关系等级 / 亲密度 | ✅ |
| messages | ❌ |
| memory_chunks（自动记忆） | ❌ |
| game_records 明细 | ❌ |

导入时缺的字段按默认值补齐，保持向后兼容（旧角色卡仍能导入，只是会忽略 messages）。

### 12.4 聊天图片：不落 base64

- 用户/角色在聊天里发的图片，**存为文件**：`data/uploads/chat/<uuid>.jpg`
- `messages` 表新增 `attachments` 字段（JSON 数组，存 `{type:'image', path:'/uploads/chat/x.jpg', w, h, bytes}`）
- 消息 `content` 只放文字（或空），不塞 base64
- 头像仍走 base64（属于角色域，要跟着角色卡走）

**必须说明的技术事实**：发给模型的请求体里，图片**仍然只能是 base64 data URL 或公网 URL**——
OpenAI 兼容协议没有"裸字节"这种传法。所以"不转 base64"准确的含义是：

> **数据库不存 base64**，请求时按需读取文件、临时编码，用完即弃。

这样 DB 保持轻量，也不会因为聊天图片把库撑大。若将来想彻底避免编码，只能改用支持文件引用的供应商（如部分厂商的 file_id 机制），属于另一条路。

### 12.5 多模态的前置条件

发图给模型需要该模型支持 vision。你那 332 个模型里只有一部分支持，中转也可能不转发图片。
方案：在 `providers` 增加 `supports_vision` 标记（默认 false，用户在设置里勾选），
不支持时前端禁用发图入口，避免"发了没反应"。

### 与设计文档的一处偏离（重要）

原计划是「写 `vector_v2` 影子列 → 完成后原子切换」。实现改为**逐行就地改写**，原因：

检索时向量路本来就按 `embed_model = 当前模型` 过滤，**跨模型比较从源头就不可能发生**。
既然如此，维护影子列只增加一倍向量存储（10k 块约 20MB）和一次全表 UPDATE，没有任何收益。

就地改写的性质同样安全：
- `vector` 与 `embed_model` 在同一条 UPDATE 里写入 → 任一行在任一时刻都是自洽的
- 已重建的块立刻参与向量检索，未重建的块退化为关键词检索 → 检索全程不中断
- 进程被杀不会留下脏数据，按 `memory_rebuild.status='running'` 续跑

### 一个真实缺陷（测试中发现并修复）

嵌入供应商拉取 `/v1/models` 后，代码取 `models[0]` 作为使用的模型。用户的聚合代理有 332 个模型，
`models[0]` 基本是随机一个，不是用户想用的那个。
修复：新增 `providers.preferred_model`，表单填的模型名落在这里；拉列表时不再覆盖它；
嵌入类供应商若未指定则落定列表第一个，之后可在设置里切换（多模型时出现下拉）。

同时修正触发条件：判断依据从「供应商 id 变了没」改为「**最终模型标识**变了没」，
否则同一供应商内换模型不会触发重建。供应商被 PATCH / 被删除（且是当前嵌入源）也会触发。

### 实测（20 项断言全过）

| 用例 | 结果 |
|---|---|
| 74 块全部用内置模型（512 维） | ✅ |
| 切换到自定义嵌入 → 立即返回、状态 running | ✅ 响应 < 50ms |
| 重建中检索仍可用 | ✅ `mode=hybrid`，已有 16 块先换好参与向量检索 |
| 重建中新消息立即用新模型 | ✅ `provider:6:embed-small` / 64 维 |
| 观察到中间进度（非一次性） | ✅ `partial=true` |
| 重建完成 | ✅ 74/74，1.58s |
| 切回内置 | ✅ 全部恢复 512 维 |
| 同供应商换模型也触发重建 | ✅ target 变为 `provider:6:fake` |
| 指向死端口 | ✅ 状态置 `error`，**旧向量完整保留**，检索退化关键词仍可用 |
| 进程中途被杀 → 重启续跑 | ✅ 重启后 30 块自动重建完成 |

### 已知取舍

- 重建是**单线程串行**（每批 16 条、间隔 150ms）。1 万块 + 本地模型约 1 分钟；走 API 取决于上游速率。
- 失败即中止，不做无限重试（避免对已欠费/失效的供应商刷请求）。旧向量保留，用户可手动重试。
- 重建期间向量路只覆盖已换模型的块，召回率会暂时偏低——这是「不中断」的代价，关键词路兜底。

## 十九、P4 阶段二：手机版改为完全独立（2026-11-16 01:10）

上一版 APK 只是「连电脑的壳」，不符合要求。这一版把整个数据层搬到了手机里。

### 19.1 架构：同一套路由，两套实现

```
lib/api.ts
  ├─ 浏览器  → fetch('/api/*')        → server/api.js（电脑上的 Node）
  └─ APK     → lib/local/server.ts    → 设备本地 SQLite
```

关键点：**手机版复刻了电脑端的全部路由和返回结构**（`/api/bootstrap`、`/api/chat`、
`/api/characters/:id/data` …），所以 `store.tsx` 和所有组件一行都没改。

落地文件：

| 文件 | 作用 |
|---|---|
| `lib/local/sqlite.ts` | `@capacitor-community/sqlite` 连接与查询封装 |

| `lib/local/server.ts` | 路由 + 对话主流程 |

### 19.2 与电脑端的行为差异（都是有意为之）

| 项 | 电脑端 | 手机端 | 原因 |
|---|---|---|---|
| 记忆检索 | 向量 + 关键词（bge-small-zh） | **关键词 + 时间衰减** | ONNX 运行时塞进 WebView 风险高且无法在本机验证；表结构保留 `vector` 列，将来可补 |

| API Key | AES 加密 | 明文存本地库 | 手机没有 `.secret`，靠应用沙盒隔离 |
| 登录门禁 | 访问密码 | **无**（进 App 即可用） | 数据在设备沙盒内，加密码只是多一道心理门槛 |
| 角色卡导出 | 下载文件 | 系统分享 / 复制到剪贴板 | WebView 里 `a[download]` 不生效 |

## 二十、手机版四项修正（2026-11-16 08:30）

真机反馈：APK 能流畅运行。随后按反馈改了四处。

### 20.1 内置嵌入模型（手机端补齐向量检索）

原来手机端只能关键词检索，这版把 bge-small-zh 塞进了 APK：

| 环节 | 做法 |
|---|---|
| 运行时 | `onnxruntime-web` 的 **wasm-only 构建**（`onnxruntime-web/wasm`），避开 webgpu/jsep 那 30MB |
| 权重 | `public/models/bge-small-zh/model_int8.onnx`（23.9MB），与电脑端**同一份文件** |
| wasm | `public/ort/ort-wasm-simd-threaded.{mjs,wasm}`（15MB），`ort.env.wasm.wasmPaths = '/ort/'` |
| 线程 | `numThreads = 1`（多线程要 COOP/COEP 头，Capacitor 给不了） |
| 分词 | `lib/local/tokenizer.ts`，与 `server/embedding/tokenizer.js` 同一套 WordPiece |
| 池化 | CLS + L2，和电脑端一致 → 两边向量可直接比较 |
| 存储 | Float32Array → base64 存 `memory_chunks.vector`（比 JSON 省一半） |
| 检索 | 向量路 + 关键词路 + RRF(k=60)，阈值 0.38 / 相对 12%，与电脑端同一套参数 |
| 降级 | 模型加载失败自动退回关键词，并在 `/api/memory/status` 里标 `embed.degraded` |
| 预热 | `ensureReady()` 后台 `warmup()`，避免第一条消息卡几秒 |

**踩到的坑**：Next 会把 onnxruntime 的 wasm 当静态资源再发一份（15MB 重复）。
因为运行时已把 `wasmPaths` 指到 `/ort/`，那份用不到 —— 在 `scripts/export-copy.mjs` 里删掉，APK 从 52MB 降到 37MB。

**验证**：用一个临时 Next 页面（`app/embedtest`，验证完已删）在真实构建产物里跑嵌入：
`dim=512 / norm=1.000000 / 相近 0.7902 / 无关 0.3284`，无 console 报错。这证明了「同一份权重在 WebView 的 WASM 里能跑出和 Node 一致的结果」。

### 20.2 逐字流式

`lib/local/llm.ts` 新增 `chatStream()`：先试 `fetch` 读 SSE（真流式），失败再退回 CapacitorHttp 整段 + 前端按小片吐出（视觉上仍是逐字）。

- 真流式路径需要服务端允许 CORS（`Origin: https://localhost`）。
- 兜底路径实测有 13 次 delta 回调，看起来就是正常打字。

### 20.3 登录门禁

手机端从「无门禁」改为：

- 首次启动：填称呼 + 密码（≥4 位）+ 确认 → SHA-256(salt+password) 存 settings
- 之后每次打开：「欢迎，{称呼}」+ 密码
- `authed` 是**内存态**，App 重启即失效；不写 cookie、不落盘

### 20.4 设置入口

从底部第四个 tab 改为**右上角浮动圆钮**（`fixed right-3 top-2.5`），三个页面头部都加了 `pr-14` 让位。
